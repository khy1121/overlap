### 0-1. 🔴 새 배포 직후 흰 화면 (MIME type "text/html")
`2026-11-02` · 커밋 `2ea2e8c`, `2551214`, 후속 `dd34561`

**프로젝트에서 발생한 문제**
- 새 버전을 배포한 직후 사용자 화면이 하얗게 비고 앱이 전혀 열리지 않았습니다.
- 콘솔 오류는 다음과 같았습니다.
  ```
  Failed to load module script: Expected a JavaScript-or-Wasm module script
  but the server responded with a MIME type of "text/html".
  ```

**문제 해결 과정 및 방법**
1. 운영 사이트에 없는 파일(`/assets/does-not-exist.js`)을 curl로 요청해 봤습니다. 404가 아니라 **200 text/html**이 돌아왔습니다.
2. 원인이 확인됐습니다.
   - SPA rewrite가 모든 경로를 `index.html`로 보내고 있었습니다.
   - 배포 때마다 해시가 붙은 JS 파일 이름이 바뀝니다. 열려 있던 예전 화면이나 PWA 캐시가 예전 JS를 요청하면 HTML을 받았습니다.
   - 서비스 워커가 그 HTML을 asset 캐시에 넣어 버리면 새로고침해도 계속 깨질 수 있었습니다.
3. 고친 내용
   - **`vercel.json`**
     - rewrite 대상에서 `assets/`, `icons/`, `brand/`, `sw.js`, `manifest.webmanifest`, `favicon.svg`를 제외했습니다. 이제 없는 파일은 진짜 404가 됩니다.
     - `/assets`는 1년 immutable 캐시, `sw.js`는 `no-cache`로 설정했습니다.
   - **`public/sw.js`**: v2로 올려 예전 캐시를 지우고, `text/html` 응답은 캐시에 넣지 않게 했습니다.
   - **`index.html` / `main.jsx`**: `/assets` 로드에 실패하면 한 번만 자동 새로고침합니다. 무한 반복은 막았습니다.
4. 정규식의 `$`를 지우는 sed가 이스케이프 문제로 적용되지 않은 채 커밋됐습니다. 그래서 `2551214`에서 다시 고쳤습니다.
5. 후속 예방책으로 "새 버전이 있어요 · 새로고침" 배너를 넣었습니다. 30분마다, 그리고 앱으로 돌아올 때마다 최신 `index.html`의 asset 해시와 비교합니다.

**결과 및 배운점**
- 운영에서 다시 확인했습니다. 없는 asset은 404, 페이지 경로는 200 HTML, 실제 JS는 200과 1년 캐시, `sw.js`는 no-cache가 나왔습니다.
- 이미 흰 화면이 된 기기는 한 번 새로고침하거나 사이트 데이터를 지우도록 안내했습니다.
- **배운점**
  - SPA rewrite는 정적 asset 경로를 반드시 제외해야 합니다.
  - 서비스 워커는 응답의 content-type을 확인한 뒤에 캐시해야 합니다.
  - 배포 직후 열려 있던 옛 화면이 어떻게 될지까지 설계해야 합니다.

### 0-2. 🔴 카카오 로그인 KOE205 오류로 로그인 불가
`2026-11-02` · 커밋 `b29947a` (출시 전 발견)

**프로젝트에서 발생한 문제**
- "카카오로 시작하기"를 누르면 카카오 에러 페이지가 떴습니다.
  > 잘못된 요청 (KOE205) Overlap 서비스 설정에 오류가 있어, 이용할 수 없습니다.

**문제 해결 과정 및 방법**
1. 처음에는 비즈 앱이 아니면 이메일이 필요 없다고 판단했는데, 이 판단은 틀렸습니다.
2. 원인
   - Supabase Kakao provider는 로그인 요청에 `scope=account_email profile_image profile_nickname`을 **항상** 넣습니다.
   - 그런데 카카오 앱에는 이메일 동의 항목이 없었습니다.
3. `scopes` 파라미터로 `account_email`을 빼 보려 했지만 빠지지 않고 덧붙기만 했습니다(실패한 시도).
4. 카카오 앱을 **개인 개발자 비즈 앱**으로 전환하고, "카카오계정(이메일)"을 **선택 동의**로 추가했습니다.
5. Supabase의 "Allow users without an email"을 켜 두어, 이메일 제공을 거부해도 로그인되게 했습니다.
6. 마이그레이션 `0007`로 카카오 사용자 이름(`name`·`nickname`)과 사진(`picture`)을 프로필에 채우게 했습니다.

**결과 및 배운점**
- KOE205가 사라지고 카카오 로그인이 정상 동작했습니다.
- **배운점**: Supabase 소셜 provider는 고정 scope를 보냅니다. provider 쪽 동의 항목을 그 scope에 맞춰야 합니다.

### 0-3. 🔴 다른 사람의 일정을 추가·수정·삭제할 수 있었음 (권한)
`2026-11-02` · 커밋 `cf84451`, 마이그레이션 `0004_own_schedule_only.sql`

**프로젝트에서 발생한 문제**
- 약속 화면에 "이 사람 입력 모두 지우기"와 "계정 없는 사람(게스트) 추가"가 있었습니다.
- 그래서 남의 일정을 지우거나 대신 입력할 수 있었습니다.

**문제 해결 과정 및 방법**
1. 기존 RLS(`0001`)를 확인했습니다. 다음 정책들이 있어서, 약속 멤버는 게스트를 추가할 수 있었고 만든 사람은 다른 참여자의 일정을 고치거나 지울 수 있었습니다.
   - `members add guests`
   - `edit self, guests, or as owner`
   - `delete self, guests, or as owner`
2. 화면에서 게스트 추가와 남의 일정 편집을 없애고 "내 입력 지우기"만 남겼습니다. 관련 함수 export도 지웠습니다.
3. `0004` 마이그레이션으로 `participants`의 insert·update·delete를 **`user_id = auth.uid()`인 본인 행**으로만 한정했습니다.
4. 적용 전에 운영 DB 정책이 `0001`과 같은지 조회했습니다. 적용 후에는 `pg_policies`로 결과를 확인했습니다.

**결과 및 배운점**
- 화면과 서버 양쪽에서 본인 일정만 편집할 수 있게 됐습니다.
- **배운점**: 권한은 UI에서 버튼을 숨기는 것만으로는 부족합니다. 반드시 DB(RLS)에서 강제해야 합니다.

### 0-4. 🔴 카카오톡 초대 링크가 localhost로 열림
`2026-11-11 ~ 11-12` · 커밋 `fb5c39a` + 카카오 콘솔 설정

**프로젝트에서 발생한 문제**
- "카카오톡으로 초대 보내기"로 받은 링크를 누르면 `localhost`로 열려서, 초대받은 사람이 약속에 들어갈 수 없었습니다.

**문제 해결 과정 및 방법**
1. **1차 (코드)**
   - 로컬 개발 서버에서 초대를 보내면 링크가 `window.location.origin`, 즉 localhost로 만들어지는 문제를 발견했습니다.
   - `src/lib/site.js`의 `APP_ORIGIN`을 만들었습니다. localhost에서도 공유 링크는 항상 배포 주소를 쓰게 했고, 초대·친구 코드·캘린더 링크에 모두 적용했습니다.
2. **2차 (근본 원인)**
   - 운영 사이트에서 카카오 공유 호출(`Kakao.Share.sendDefault`)을 가로채 인자를 확인했습니다. 앱은 이미 `https://overlap-liard.vercel.app/?m=...`을 정확히 보내고 있었습니다. 이때 실제 메시지는 보내지 않았습니다.
   - 카카오 콘솔 **앱 → 제품 링크 관리 → 웹 도메인**을 확인했습니다. 등록된 곳은 `http://localhost:5173`(기본)과 `khy1121.github.io`뿐이었습니다.
   - 카카오는 **등록되지 않은 도메인의 링크를 기본 도메인으로 바꿔서** 보냅니다.
3. 웹 도메인에 `https://overlap-liard.vercel.app`을 추가했습니다.
4. 기본 도메인을 배포 주소로 바꾸는 것은 운영 설정 변경이라 사용자가 직접 하도록 안내했습니다.

**결과 및 배운점**
- 사용자가 폰에서 초대 링크가 배포 주소로 제대로 열리는 것을 확인했습니다.
- **배운점**
  - 카카오에는 도메인 설정이 두 군데 있습니다. JS SDK 도메인(플랫폼 키)과 링크 이동 허용 도메인(제품 링크 관리)은 따로 관리됩니다.
  - 앱이 보내는 값부터 확인했더니 원인을 코드와 설정으로 빠르게 나눌 수 있었습니다.

### 0-5. 🟠 모바일에서 스크롤과 칸 칠하기가 겹침 (두 번에 걸친 개선)
`2026-11-02` 커밋 `227a15d`, `2936b40` → `2026-11-11` 커밋 `d5f0661`

**프로젝트에서 발생한 문제**
- **1차 (11/2, 사용자 보고)**
  - 폰에서 시간표를 스크롤하면 손가락이 닿은 칸이 칠해졌습니다.
  - 당시에는 칠할 때마다 바로 서버에 저장돼서, 원치 않는 일정 데이터가 생겼습니다.
- **2차 (11/11, 실사용자 의견)**: "내 일정을 수정할 때 스크롤하는 영역과 일정 선택하는 영역이 겹쳐서 불편하다." 칠하기 모드에서는 칸 위에서 스크롤이 막혀, 왼쪽 시간 눈금(약 38px)만 잡아야 스크롤됐습니다.

**문제 해결 과정 및 방법**
1. **1차**
   - 터치 기기에서는 시간표를 기본으로 잠갔습니다. "내 일정 등록/수정"을 눌러야 칠하기가 시작됩니다.
   - 칠한 내용은 **저장을 눌러야만** 서버에 반영되게 바꿨습니다(draft → 저장/취소).
2. **2차: 길게 눌러 칠하기**
   - 칸을 그냥 쓸면 스크롤됩니다.
   - 톡 치면 한 칸만 칠합니다.
   - 0.32초 길게 누르면 드래그 칠하기가 시작됩니다. 누른 채 8px 넘게 움직이면 취소됩니다.
3. 구현 방법
   - 시간표 CSS를 `touch-action: pan-x pan-y`로 바꿨습니다.
   - 드래그 칠하기 중일 때만 non-passive `touchmove`에서 `preventDefault`를 호출해 스크롤을 막습니다.
   - 길게 누를 때 뜨는 메뉴(`contextmenu`)와 iOS 콜아웃도 막았습니다.

**결과 및 배운점**
- 스크롤과 칠하기가 손동작으로 구분돼서, 별도 잠금 없이 둘 다 자연스럽게 됩니다.

### 4-1. 🟠 약속 기간이 하루 단위로만 정해짐 + 확정 시각 계산 오류
`2026-11-11` · 커밋 `44c219e`, 마이그레이션 `0017_meeting_start_end_hour.sql`

**프로젝트에서 발생한 문제**

**문제 해결 과정 및 방법**
1. 데이터 모델에 `start_hour`(첫날 시작)와 `end_hour`(마지막 날 끝)를 추가했습니다. `create_meeting` RPC도 새 인자를 받게 바꿨고, 기본값은 null이라 하위 호환됩니다.
2. 시간표의 세로 범위
   - 첫날, 가운데 날, 마지막 날의 시간대를 모두 합친 범위로 그립니다(`rowFrom`·`rowTo`).
   - 그날 범위 밖의 칸은 칠할 수 없는 빗금 칸(`blocked`)으로 표시합니다.
3. 추천 계산(`evaluate`)은 막힌 칸을 지나는 시간을 후보에서 뺍니다. Google 캘린더 가져오기도 막힌 칸은 건너뜁니다.
4. 이 과정에서 **확정 시각 계산 오류**를 발견했습니다.
   - 칸 번호는 시간표 첫 행 기준인데, `confirmedTime`은 `from_hour`를 기준으로 계산하고 있었습니다.
   - 그래서 첫날 시작이 하루 시간대보다 이르면 확정 시각이 어긋났습니다.
   - `min(from_hour, start_hour)` 기준으로 고쳤습니다.
5. 설정이 맞는지 검사하는 `rangeError`를 두었습니다. 예를 들어 끝이 시작보다 빠르거나, 기간이 최대 14일을 넘으면 안내합니다.

**결과 및 배운점**
- "11/12 12:00 – 11/14 22:00" 같은 기간이 가능해졌습니다. 3일 약속에서 막힌 칸과 헤더 표시를 확인했습니다.
- **배운점**
  - 좌표계(칸 번호의 기준점)를 바꾸면, 그 좌표를 쓰는 모든 곳(확정 시각, 캘린더 링크, 추천)을 함께 확인해야 합니다.
  - DB 변경은 기본값으로 하위 호환되게 넣었습니다.

3. **iOS 사파리는 `user-scalable=no`를 무시**합니다. 그래서 `gesturestart` 이벤트에서 직접 `preventDefault`를 호출했습니다.

**결과 및 배운점**

- **배운점**

  - 접근성(저시력 사용자)과 맞바꾸는 결정이라는 점을 함께 기록해 둬야 합니다.

### 6-1. 🟢 운영 변경이 자동 승인에서 반복 차단됨
`2026-11-02`, `2026-11-11 ~ 12`

**프로젝트에서 발생한 문제**
- AI 개발 도구의 자동 승인 모드가 다음 작업을 막았습니다.
  - 운영 DB 마이그레이션(`0005`~`0016`, `0018` 첫 시도)
  - Edge Function 배포
  - 비밀값 등록
  - Vercel 운영 재배포
  - 카카오 기본 도메인 변경
- 그래서 "코드는 배포됐는데 DB는 아직"인 구간이 여러 번 생겼습니다.

**문제 해결 과정 및 방법**
1. 막히면 화면 코드를 먼저 커밋했습니다. 서버가 준비되지 않았을 때는 "서버 업데이트가 아직이에요" 같은 대체 문구가 나오게 했습니다.
2. 사용자가 승인하면 반영했습니다. 비밀값과 일부 설정은 사용자가 대시보드에서 직접 입력했습니다.

**결과 및 배운점**
- 모든 운영 변경은 사용자 승인 아래 이뤄졌습니다.
- **배운점**
  - 화면 코드는 DB 변경보다 먼저 배포될 수 있다고 보고 **하위 호환**으로 짜야 합니다. 예를 들어 RPC의 새 인자에는 기본값을 둡니다.
  - 운영 설정 변경은 사람이 최종 확인하는 흐름이 안전합니다.

### 6-2. 🟢 커밋에 AI 작성 표기가 들어가 히스토리 재작성
`2026-11-02`

**프로젝트에서 발생한 문제**
- 이미 푸시한 커밋 8개에 AI 작성 표기 줄이 들어 있어서, 사용자가 전부 지워 달라고 요청했습니다.

**문제 해결 과정 및 방법**
1. 백업 브랜치를 만든 뒤 해당 줄만 지우도록 커밋 메시지를 재작성했습니다.
2. 코드 내용이 백업과 같은지 비교한 뒤 강제 푸시했습니다.
3. 앞으로 표기를 넣지 않도록 규칙을 기록했습니다.

**결과 및 배운점**
- 표기는 사라졌지만 커밋 해시가 모두 바뀌었습니다.
- **배운점**
  - 커밋 메시지 규칙은 첫 커밋 전에 정해야 합니다.
  - 이후에는 "기능 하나 = 커밋 하나 = 푸시 하나" 원칙으로 작게 나눠 올립니다.
